# 1. یافته‌های قطعی که این plan بر اساس آن‌ها ساخته شده

این بخش از سورس فعلی استخراج شده و مبنای اولویت‌بندی است.

## 1.1 Execution definition قبل از persistence تغییر می‌کند

در `core/workflow_store.py`، definition با:

```python
redact_inputs(asdict(definition))
```

ذخیره می‌شود.

`redact_inputs()` دو رفتار دارد:

1. keyهایی مانند `secret`، `token`، `idempotency_key` و مشابه را به `<redacted>` تبدیل می‌کند.
2. تمام stringها را به 2000 کاراکتر محدود می‌کند.

اما `WorkflowExecutor` همان definition ذخیره‌شده را دوباره برای اجرای واقعی می‌خواند.

نتیجه:

```text
definition submitted by caller
        ↓
redaction/truncation
        ↓
SQLite
        ↓
executor
        ↓
modified definition is executed
```

این behavior برای durable execution قابل قبول نیست.

---

## 1.2 `run_durable_job.idempotency_key` در مسیر اجرای durable خراب می‌شود

`idempotency_key` در secret markerها قرار دارد و هنگام persistence به `<redacted>` تبدیل می‌شود.

بنابراین چند workflow مستقل می‌توانند در زمان اجرا عملاً همین key را به JobStore بدهند:

```text
<redacted>
```

و collision یا `idempotency_conflict` ایجاد شود.

این bug باید قبل از هر توسعه orchestration بسته شود.

---

## 1.3 Lease با timeout واقعی step هماهنگ نیست

- default lease: 30 ثانیه
- max lease: 300 ثانیه
- step timeout: تا 3600 ثانیه
- builtin verification: تا 1800 ثانیه

در زمان اجرای خود action heartbeat دوره‌ای وجود ندارد.

پس یک step سالم و طولانی می‌تواند بعد از موفقیت، هنگام checkpoint با `workflow_lease_expired` مواجه شود.

---

## 1.4 Durable reconciliation هنوز به result گم‌شده وابستگی دارد

در action surface postconditionهایی مانند:

```text
git_head_from_result
git_index_contains_from_result
job_succeeded_from_result
```

وجود دارند.

این‌ها برای مسیر عادی داخل همان process مفیدند، اما اگر side effect رخ دهد و result قبل از checkpoint گم شود، داده لازم برای ساخت expected state دیگر موجود نیست.

Reconciliation durable باید بر evidenceای تکیه کند که **قبل از side effect** persist شده یا از یک idempotency identity پایدار قابل بازیابی باشد.

---

## 1.5 Cancellation فعلی بیشتر "توقف ادامه workflow" است تا cancellation واقعی

`workflow_cancel` می‌تواند aggregate workflow را `cancelled` کند، اما action جاری:

- signal دریافت نمی‌کند
- durable job زیرمجموعه الزاماً cancel نمی‌شود
- verification زیرمجموعه الزاماً متوقف نمی‌شود

پس side effect جاری ممکن است بعد از cancel کامل شود.

---

## 1.6 Workflow durable job دوباره polling پرهزینه ایجاد کرده

`_run_durable_job()` تقریباً هر 100ms `store.get()` می‌زند.

این با primitive موجود `job_wait(after_version, timeout)` هم‌راستا نیست و در jobهای طولانی SQLite pressure غیرضروری ایجاد می‌کند.

---

## 1.7 Workflow worker فقط یک window محدود از history را scan می‌کند

`scripts/workflow_worker.py` از:

```python
store.list(limit=100)
```

استفاده می‌کند و بعد در Python فقط queuedها را جدا می‌کند.

Queued workflow قدیمی‌تر ممکن است خارج از 100 رکورد جدیدتر بماند و starvation بگیرد.

---

## 1.8 Workflow persistence retention مستقل ندارد

برای jobs، artifacts، backups و audit budget وجود دارد، ولی workflow DB شامل:

- workflows
- steps
- operations
- events

retention مشخص و budget مستقل ندارد.

---

## 1.9 `workflow_plan` contract با behavior یکی نیست

docstring می‌گوید plan را validate می‌کند، ولی custom workflow در مرحله plan تمام action validation نهایی را انجام نمی‌دهد.

Plan ممکن است موفق شود و start همان definition را رد کند.

---

## 1.10 بعضی workflow actionها در surface هستند ولی executor adapter ندارند

```text
desktop_semantic_action
browser_action
```

allowlisted هستند اما handler فعلی عمداً `workflow_adapter_required` می‌دهد.

Action unavailable نباید مثل action executable به caller معرفی شود.

---

## 1.11 LSP read tools capability واقعی بزرگ‌تر از annotation آن‌هاست

ابزارهای read-only language اجازه `command: list[str]` دارند و آن command با `subprocess.Popen` اجرا می‌شود.

پس caller می‌تواند از یک tool با annotation خواندنی برای spawn executable دلخواه استفاده کند.

---

## 1.12 LSP one-shot client sequencing کاملاً protocol-correct نیست

Client فعلی initialize، initialized، request، shutdown و exit را قبل از خواندن initialize response پشت سر هم روی stdin می‌فرستد.

بعضی language serverها این را تحمل می‌کنند، اما sequence رسمی LSP نیست.

همچنین برای document methodها `didOpen` وجود ندارد.

---

## 1.13 Full pytest روی basetemp فعلی Windows قابل اتکا نیست

`pyproject.toml`:

```toml
--basetemp=.agent_state/pytest-tmp
```

دارد.

روی سیستم فعلی این path با `WinError 5 Access is denied` باعث failure قبل از اجرای suite شد.

با basetemp مستقل، 83 تست workflow بررسی‌شده پاس شدند.

# 2. اصول غیرقابل مذاکره v0.2.5

## اصل A: Execution truth با public view یکی نیست

هیچ redaction، truncation یا formatting نمایشی نباید payloadی را که executor اجرا می‌کند تغییر دهد.

## اصل B: Secret literal در durable workflow نباید بی‌قاعده persist شود

اگر یک action واقعاً secret می‌خواهد:

- یا opaque secret reference استفاده شود
- یا durable execution آن action fail-closed شود

نه اینکه secret پاک شود و مقدار پاک‌شده اجرا شود.

## اصل C: Postcondition durable باید قبل از side effect قابل materialize باشد

اگر recovery برای موفقیت به resultی نیاز دارد که ممکن است گم شود، recovery واقعی نیست.

## اصل D: Lease فقط قفل نیست، fencing contract است

Executorی که lease را از دست داده حق publish کردن checkpoint نهایی ندارد.

## اصل E: Cancel باید semantics دقیق داشته باشد

باید مشخص باشد:

- immediate cancellation
- cooperative cancellation
- deferred cancellation

کدام action چه رفتاری دارد.

## اصل F: uncertain هرگز replay کورکورانه نمی‌شود

این invariant فعلی حفظ می‌شود.

## اصل G: state نامحدود ممنوع است

Workflow events/history نیز مانند jobs/artifacts budget و retention می‌گیرد.

## اصل H: read-only annotation باید با capability واقعی tool سازگار باشد

یک tool read-only نباید arbitrary executable launcher باشد.

# 5. Phase B - Separate Durable Execution Payload From Public Projection

این مهم‌ترین refactor نسخه است.

## هدف

سه مفهوم از هم جدا شوند:

```text
Execution Definition
Public Projection
Audit/Event Metadata
```

هیچ‌کدام نباید به جای دیگری استفاده شود.

---

## 5.1 Schema v2

`SCHEMA_VERSION` از 1 به 2 افزایش یابد.

پیشنهاد حداقلی:

```text
workflows
  workflow_id
  ...
  definition_json               legacy/public compatibility
  execution_definition_json     exact durable execution payload
  execution_definition_hash     SHA-256 canonical payload
  execution_compatible          0/1
  schema_version                optional per-record marker
```

برای new workflow:

- `execution_definition_json`: canonical و بدون truncation
- `definition_json`: redacted/bounded projection فقط برای status compatibility
- hash از execution definition واقعی ساخته شود

`WorkflowExecutor` فقط از `execution_definition_json` بخواند.

`workflow_status` فقط public projection را برگرداند.

---

## 5.2 Legacy migration باید fail-closed باشد

داده v1 قبلاً ممکن است:

- secret را از دست داده باشد
- string را truncate کرده باشد

این داده قابل بازسازی قطعی نیست.

بنابراین migration نباید وانمود کند execution payload قدیمی معتبر است.

Rule:

```text
terminal workflow
    -> readable history, no problem

non-terminal legacy workflow with no exact execution payload
    -> execution_compatible = false
    -> execute/resume rejected with actionable error
    -> never replay from redacted definition
```

Error پیشنهادی:

```text
workflow_legacy_definition_unrecoverable
```

---

## 5.3 Redaction API جدید

`redact_inputs()` دیگر برای ساخت execution record استفاده نشود.

دو API جدا:

```python
canonical_execution_definition(...)
public_workflow_projection(...)
```

Public projection می‌تواند:

- secret field را redact کند
- string بزرگ را truncate کند
- output size را bound کند

ولی execution payload را تغییر نمی‌دهد.

---

## 5.4 Secret handling

Heuristic key matching به تنهایی برای durable secret مناسب نیست.

تصمیم v0.2.5:

1. `idempotency_key` secret محسوب نشود.
2. docs صریح بگوید idempotency key نباید credential باشد.
3. ActionDescriptor برای secret واقعی `secret_fields` داشته باشد.
4. literal secret در durable workflow فعلاً fail-closed شود مگر secret-reference contract داشته باشد.
5. future secret support با opaque reference انجام شود، نه plaintext arbitrary secret در workflow JSON.

مدل آینده:

```json
{
  "token": {
    "$secret_ref": "github-release-token"
  }
}
```

v0.2.5 لازم نیست secret vault عمومی بسازد، ولی نباید literal secret را خراب و سپس اجرا کند.

---

## 5.5 Event/result redaction

Result و evidence همچنان قبل از ذخیره audit/public redacted شوند.

اما fingerprint باید از canonical original data در نقطه امن ساخته شود، نه از value redacted شده، وقتی identity operation به original value وابسته است.

# 6. Phase C - Lease Heartbeat, Fencing, and Safe Release

## هدف

یک action چنددقیقه‌ای نباید به خاطر TTL کوتاه lease خودش را از دست بدهد.

---

## 6.1 Heartbeat lifecycle

برای زمان اجرای هر action یک lease heartbeat فعال شود.

ساختار پیشنهادی:

```text
acquire lease
    ↓
start heartbeat
    ↓
checkpoint operation RUNNING
    ↓
execute action
    ↓
stop heartbeat
    ↓
verify lease token still current
    ↓
publish result/evidence
```

Interval:

```text
min(max(ttl / 3, 1s), 10s)
```

با jitter کوچک در صورت داشتن چند worker، ولی deterministic testها نباید به jitter وابسته باشند.

---

## 6.2 Lease loss behavior

اگر heartbeat نتواند lease را renew کند:

- executor نباید succeeded/failed نتیجه side effect را با lease stale publish کند.
- stale token هرگز lease جدید را overwrite/delete نکند.
- operation باید توسط recovery بعدی uncertain شود.

Event پیشنهادی:

```text
workflow_lease_lost
```

---

## 6.3 Safe release

`finally: release_lease(...)` نباید exception اصلی را با token mismatch جدید mask کند.

API پیشنهادی:

```python
release_lease_if_current(workflow_id, lease_token) -> bool
```

رفتار:

- same token: delete و True
- lease missing: False
- another token owns it: False
- هرگز lease owner جدید را حذف نکند

`require_lease()` همچنان strict باقی بماند.

---

## 6.4 Deterministic tests

برای تست بهتر clock injection اضافه شود یا lease timing helper قابل fake شدن باشد.

تست‌های wall-clock چندثانیه‌ای زیاد ساخته نشوند.

---

## فایل‌ها

```text

core/workflow_store.py
core/workflow_models.py
tests/test_workflow_lease_heartbeat.py
tests/test_workflow_leases.py
tests/test_workflow_crash_recovery.py
```

## Acceptance

- step 1800s از نظر contract با lease 30s معتبر باشد چون heartbeat renew می‌کند.
- stale executor بعد از lease takeover checkpoint نکند.
- release stale token lease owner جدید را خراب نکند.
- exception اصلی executor در finally mask نشود.

# 7. Phase D - Real Cancellation Semantics

## هدف

Cancellation از یک state flip به contract مشخص تبدیل شود.

---

## 7.1 State model

پیشنهاد:

```text
RUNNING
  ↓ cancel request
CANCELLING
  ↓ action stopped / action returned and evidence persisted
CANCELLED
```

برای queued/paused:

```text
QUEUED -> CANCELLED
PAUSED -> CANCELLED
```

---

## 7.2 Workflow schema

فیلدهای پیشنهادی:

```text
cancel_requested_at
cancel_reason
```

در صورت نیاز:

```text
cancel_requested_by
```

اما actor باید bounded و audit-safe باشد.

---

## 7.3 Action cancellation capability

ActionDescriptor مشخص کند:

```text
cancel_mode:
  immediate
  cooperative
  deferred
```

مثال:

```text
run_durable_job   cooperative
check_http        deferred/bounded timeout
git_commit        deferred, never interrupt in unknown side-effect window
git_stage         deferred
verify_changes    cooperative after verification service gains cancellation
apply_patch       deferred transactional section
```

---

## 7.4 ActionContext

برای شکستن coupling و پشتیبانی cancellation/recovery:

```python
ActionContext:
    workflow_id
    operation_id
    lease_token
    is_cancel_requested()
    persist_external_ref(...)
    persist_intent_evidence(...)
```

handler دیگر فقط `arguments, timeout` نگیرد.

---

## 7.5 Durable job cancellation

بعد از submit، `job_id` فوراً در operation external reference persist شود.

در wait loop:

- cancellation flag check شود
- `JobStore.cancel(job_id)` فراخوانی شود
- terminal job state persist شود
- سپس workflow CANCELLED شود

---

## 7.6 Side effect completed during cancel

اگر cancel هنگام یک mutation غیرقابل قطع درخواست شد و mutation موفق تمام شد:

- operation باید `succeeded` ثبت شود
- evidence باید حفظ شود
- workflow remaining steps را اجرا نکند
- workflow سپس `cancelled` شود

این از دروغ گفتن درباره side effect جلوگیری می‌کند.

---


## Acceptance

- mutation موفق قبل از cancel request در history از بین نرود.
- cancel شدن workflow باعث replay step نشود.

# 8. Phase E - Durable Reconciliation Without Lost Result Dependency

این دومین بخش بسیار حساس معماری است.

## هدف

هر mutating action قبل از side effect، reconciliation intent کافی persist کند.

---

## 8.1 حذف durable `*_from_result` semantics

این kindها برای durable recovery مناسب نیستند:

```text
git_head_from_result
git_index_contains_from_result
job_succeeded_from_result
```

اگر در-process helper باقی بمانند نباید persisted durable postcondition باشند.

Persisted form باید canonical و مستقل از result گم‌شده باشد.

---

## 8.2 git_stage

قبل از mutation می‌دانیم:

- repo
- requested paths

پس persisted postcondition:

```json
{
  "kind": "git_index_contains",
  "expected": {
    "repo": "...",
    "paths": ["..."]
  }
}
```

باشد.

---

## 8.3 git_commit

برای commit باید قبل از side effect evidence کافی ثبت شود.

قبل از `git commit`:

```text
before_head
staged_tree_hash = git write-tree
message_hash
repo
```

persist شود.

Postcondition جدید:

```text
git_commit_effect
```

Reconciler بررسی کند:

1. HEAD هنوز before_head است -> commit انجام نشده.
2. HEAD تغییر کرده.
3. parent HEAD == before_head.
4. tree HEAD == staged_tree_hash.
5. commit message hash == message_hash.

فقط در حالت conclusive همه شروط، success ثبت شود.

اگر branch توسط عامل دیگری جلو رفته باشد و evidence دقیق match نکند، uncertain باقی بماند.

---

## 8.4 run_durable_job


# 22. نتیجه معماری

لایه orchestration فعلی پایه‌های خوبی دارد:

- explicit state machine
- SQLite persistence
- CAS versioning
- lease token
- operation journal
- no blind uncertain replay
- typed action allowlist
- postcondition concept
- crash-recovery tests

مشکل اصلی این نیست که architecture باید دور ریخته شود.

مشکل این است که چند boundary هنوز با هم قاطی شده‌اند:

```text
execution data ↔ redacted display data
lease ownership ↔ long-running execution
action result ↔ recovery evidence
workflow cancelled ↔ current side effect cancelled
read-only tool ↔ arbitrary process capability
```

v0.2.5 باید دقیقاً این boundaryها را جدا و enforce کند.

بعد از آن، اضافه کردن workflowهای قوی‌تر، browser/desktop adapters، deployment adapters یا warm LSP منطقی می‌شود.
